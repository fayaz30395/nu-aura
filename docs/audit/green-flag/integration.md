| INT-1 | **HIGH** | Kafka / Payroll | `DeadLetterHandler.handleDeadLetter` `@KafkaListener` topics array (`DeadLetterHandler.java` L112–119) omits `KafkaTopics.PAYROLL_PROCESSING_DLT`. Messages silently expire after the 7-day retention. A failed payroll run becomes invisible work loss. | Add `KafkaTopics.PAYROLL_PROCESSING_DLT` to the `topics = {…}` array of `handleDeadLetter` in `backend/src/main/java/com/nulogic/infrastructure/kafka/consumer/DeadLetterHandler.java`. One-line change. | dev | OPEN |
| INT-2 | **HIGH** | DocuSign integration | `DocuSignApiClient` (L123, L176) and `DocuSignAuthService` (L276) build `HttpRequest`s with **no `.timeout(...)`**. `HttpClient.connectTimeout(10s)` only bounds connection establishment; `java.net.http` response wait is **infinite** by default. | A hung DocuSign endpoint blocks the calling thread forever (request thread or scheduled-job thread), leaking threads/DB connections until pod restart. | Add `.timeout(Duration.ofSeconds(30))` to every `HttpRequest.newBuilder()` chain in `DocuSignApiClient.java` and `DocuSignAuthService.java`. | dev | OPEN |
| INT-3 | **HIGH** | Kafka publish path | No transactional outbox (ADR list has no outbox decision; zero `outbox` references in code). `EventPublisher.sendEvent` correctly propagates failures (R2-004 fix), but **15 of 16 call sites ignore the returned `CompletableFuture`** (e.g. `WikiPageService` L461, `ExitManagementService` L303, `AssetManagementService` L485). Only `PayrollController` (L148–161) blocks with `.get()` and compensates (rolls run back to DRAFT). Producer `max.block.ms=5000` / `delivery.timeout.ms=10000` bounds the wait, so when the broker is down the send fails fast — and the event is **dropped with only an ERROR log**. | Broker outage at publish time silently loses: employee-lifecycle events (downstream onboarding/offboarding automation), approval events (notifications to requesters), audit events (compliance gaps), fluence-content events (ES index drift vs PostgreSQL). DB commit succeeds; event never exists. | Short-term (pre-launch): for state-changing events (approval, employee-lifecycle), follow the `PayrollController` pattern — `.get()` within the request and surface/compensate failure; for audit/fluence, add an `exceptionally` handler that persists the payload to `failed_kafka_events` (table already exists) for replay. Long-term: ADR + transactional outbox table polled by a publisher job. | architect + dev | OPEN |
| INT-4 | **HIGH** | Webhooks | Retry sweep (`WebhookDeliveryService.processRetries`) only selects `status = 'RETRYING' AND nextRetryAt <= now` (`WebhookDeliveryRepository` L26–47). Rows stuck in `PENDING` (saved, pod crashed before first attempt) or `DELIVERING` (crash mid-attempt) match no query and are **never retried or failed** — invisible forever. | Pod restart/crash during webhook dispatch silently drops deliveries while the row claims PENDING/DELIVERING. Violates ADR-004's at-least-once delivery promise. | Add a stale-row sweep to `processRetries` (or a second scheduled method): `UPDATE webhook_deliveries SET status='RETRYING', next_retry_at=now WHERE status IN ('PENDING','DELIVERING') AND updated_at < now - interval '10 minutes'`. | dev | OPEN |
| INT-5 | MEDIUM | Kafka consumers | The 4 consumers `ApprovalEventConsumer`, `AuditEventConsumer`, `EmployeeLifecycleConsumer`, `NotificationEventConsumer` claim via `tryProcess()` but never `release()` on the failure path (the documented follow-up from kafka-idempotency-audit.md, not implemented). If the Redis claim succeeds and the DB write then fails, every Kafka retry **and the DLT-replayed copy** is swallowed for 24h by the idempotency TTL. | Transient DB failure converts an at-least-once retry into a silent drop for notifications, approvals side-effects, lifecycle automation, audit rows. | Copy the `claimed` flag + `idempotencyService.release(eventId)` catch-block pattern from `PayrollProcessingConsumer`/`FluenceSearchConsumer` into the 4 listeners. | dev | OPEN |
| INT-6 | MEDIUM | Redis / rate limiting | `DistributedRateLimiter.tryAcquire` fails **CLOSED** for `RateLimitType.AUTH` when Redis is down (L155–183, intentional). All other buckets fail open; per-tenant buckets have a Bucket4j in-memory fallback — AUTH has none. | Redis outage = **total login outage** (every auth request 429s) even though the rest of the API degrades gracefully. Deliberate security trade-off, but it makes Redis a hard availability dependency for sign-in. | Either accept and document in runbook (alert on `RedisHealthIndicator` DOWN as a login-outage incident), or add an in-memory Bucket4j AUTH fallback (5/min per pod) matching `tryConsumePerTenant`'s fallback pattern. | security-architect (decision) | OPEN — needs go/no-go decision |
| INT-7 | MEDIUM | Webhooks / DB pool | `dispatchEvent` (`@Async @Transactional`) and `processRetries` (`@Transactional`) execute the outbound HTTP POST **inside the DB transaction**; `deliveryRestTemplate` allows 10s connect + 30s read. | Each in-flight webhook holds a Hikari connection up to ~40s. A burst (bulk import firing N webhooks × slow endpoints) can exhaust the pool and stall unrelated requests. | Remove `@Transactional` from the dispatch path; persist delivery row in a short `REQUIRES_NEW` tx, perform HTTP outside any tx, persist result in a second short tx. | dev | OPEN |
| INT-8 | MEDIUM | Observability | Health indicators registered: `ApplicationHealthIndicator`, `DatabaseHealthIndicator`, `RedisHealthIndicator`, `WebhookHealthIndicator` (+ Spring Boot auto ES health when enabled). **No Kafka health indicator** — Spring Boot does not auto-configure one. | Broker outage is invisible in `/actuator/health`; readiness probes and uptime checks report healthy while every event publish is failing (compounds INT-3). | Add `KafkaHealthIndicator` using `KafkaAdmin.describeCluster()` with a 3s timeout; register Prometheus alert on it. Alert rules for DLT/lag already exist (`hrms-slo-alerts.yml` L171–239: `KafkaConsumerLagHigh`, `KafkaDeadLetterReceived`, `KafkaDeadLetterAccumulating`). | dev | OPEN |
| INT-9 | LOW | Webhooks | `dispatchEvent` idempotency guard `existsByWebhookIdAndEventId(webhook.getId(), eventId)` (L166) is dead code — `eventId` is a fresh `UUID.randomUUID()` generated three lines above, so the check can never match. | No real dedup: a business operation that dispatches twice (retry, double-click surviving idempotency layers) produces duplicate webhook events to consumers. Consumers can dedupe on `X-Webhook-Event-Id` only if the two events shared an id — they don't. | Derive `eventId` from the triggering domain event (e.g. caller-supplied `sourceEventId`) or delete the misleading check and document at-least-once semantics per ADR-004. | dev | OPEN |
| INT-10 | LOW | Redis cache | `CacheConfig.errorHandler()` swallows GET/PUT/**EVICT**/CLEAR errors (correct for availability — app falls through to DB, no 500s). But evictions lost during a Redis outage mean stale entries can be served after Redis recovers, until TTL expiry (named caches: 5min–24h). | Stale permissions/config served up to the cache TTL after a Redis blip that coincided with a write. | Acceptable for most caches. For the permission/RBAC caches specifically, consider tracking failed evictions and re-clearing on `RedisHealthIndicator` recovery, or keep security-critical TTLs ≤5min. | dev | ACCEPTED-RISK candidate |
| INT-11 | LOW | File storage | Upload failures throw `BusinessException` (request fails loudly — good); AV scan runs before any Drive write; mapping row persisted after upload. Crash between Drive upload and `persistDriveMapping` orphans the Drive file. `OrphanFileCleanupScheduler` exists but is **Phase-1 report-only** (logs weekly, deletes nothing, 48h age threshold). | Slow accumulation of unreachable Drive files (storage cost / data-retention hygiene); no data loss. | Promote scheduler Phase 2: auto-delete orphans older than 30 days after a dry-run period; keep the weekly report. | dev | OPEN (post-launch OK) |
| INT-12 | LOW | Redis / auth | `TokenBlacklistService` boots with `redisAvailable=false`; first probe runs at +5s (`@Scheduled initialDelay=5000`). Blacklist writes in the first ~5s after pod start go to the per-pod in-memory map even when Redis is healthy. | Logout/revocation issued in a pod's first seconds isn't visible to other pods until tokens expire. Tiny window, multi-pod only. | Probe once synchronously in the constructor (best-effort, 2s Redis timeout already configured) before relying on the scheduled probe. | dev | OPEN (post-launch OK) |
| INT-13 | LOW | Elasticsearch | `FluenceSearchService` queries ES directly with no DB fallback; when ES is unreachable, `FluenceSearchController` surfaces a 5xx for search only. Indexing side is resilient: consumer releases idempotency claim on ES failure → Kafka retries → DLT; ES disabled via `app.elasticsearch.enabled=false` cleanly de-registers all beans (`@ConditionalOnProperty`). Spring Boot ES client default timeouts apply (connect 1s / socket 30s — bounded). | Fluence search feature degrades to error rather than degraded results during an ES outage; core HRMS unaffected. No data corruption (PostgreSQL remains source of truth). | Optional: catch `DataAccessResourceFailureException` in `FluenceSearchController` and fall back to `KnowledgeSearchService` (Postgres ILIKE), or return 503 + friendly UI message. | dev | OPEN (post-launch OK) |
| INT-14 | LOW | Email | Email pipeline is sound: row persisted `PENDING` → SMTP send → `SENT`/`FAILED` with `retryCount`; `EmailSchedulerService` retries tenant-scoped up to 3 attempts; SMTP timeouts tight (connect 5s / read 3s / write 5s in `application.yml` L167–169); Kafka `NotificationEventConsumer` decouples sends from business actions. Residual gap: `sendEmail` is `@Transactional` and **joins the caller's transaction** when invoked synchronously (e.g. `sendLeaveApprovalEmail` from request flows) — if the outer tx rolls back after `mailSender.send()` succeeded, the email was sent for an action that never committed, and the SENT row vanishes. | Rare ghost email (e.g. "approved" mail for a rolled-back approval); audit row for the send is also rolled back. | Mark `sendEmail` `@Transactional(propagation = REQUIRES_NEW)` or route all synchronous call sites through the Kafka notification topic (already the dominant pattern). | dev | OPEN (post-launch OK) |

## Area verdicts (pass/fail summary)

| Area | Verdict | Notes |
|------|---------|-------|
| Kafka consumer idempotency (ADR-011) | **PASS w/ caveat** | All 7 listeners use atomic SETNX claim; prior audit's 2 fixes verified in code. Caveat = INT-5 (missing `release()` in 4 consumers). `IdempotencyService` fails open on Redis outage by design (documented; DB constraints are the safety net). |
| Kafka DLQ/retry | **FAIL until INT-1** | Exponential backoff 1s→5s→25s (~36s budget) then `DeadLetterPublishingRecoverer` → `.dlt` same-partition; DLT persisted + replayable via admin API with poison-pill guard. Payroll DLT unconsumed (INT-1). |
| Broker-down at publish | **FAIL until INT-3** | Bounded fail-fast (max.block 5s) but fire-and-forget at 15/16 call sites; no outbox. Payroll alone compensates correctly. |
| Redis degradation | **PASS w/ decision item** | Cache → DB fall-through via `CacheErrorHandler` (no 500s); token blacklist in-memory fallback with recovery probe; per-tenant rate limit Bucket4j fallback. AUTH bucket fails closed = login outage (INT-6, deliberate). |
| Elasticsearch | **PASS** | Index failures retried via Kafka + DLT; no corruption (PG is truth). Search 5xx during outage (INT-13, low). |
| File storage | **PASS** | Loud upload failure, AV-scan-first ordering, tenant-scoped mapping. Orphan cleanup report-only (INT-11). |
| Email | **PASS** | Persisted + retried, tight SMTP timeouts. Minor tx coupling (INT-14). |
| Webhooks (ADR-004) | **PASS w/ caveat** | HMAC-SHA256 + dual-secret rotation, SSRF re-check at delivery, redirects blocked, circuit breaker, backoff 1/5/15/60min ×5 attempts, 10s/30s timeouts, ShedLock'd sweep. Caveats: stuck PENDING/DELIVERING rows (INT-4), HTTP-in-transaction (INT-7), dead dedup check (INT-9). |
| Observability | **PASS w/ gap** | 4 custom health indicators; DLT counters pre-registered; alert rules exist in `infra/monitoring/prometheus/rules/` (DLT received/accumulating, consumer lag, webhook/email/notification failure rates, scheduled-job liveness, SLOs) + Alertmanager wired. Gap: no Kafka health indicator (INT-8). |
| HTTP timeouts | **FAIL until INT-2** | Kafka producer 5s/10s; webhook 10s/30s; AI RestTemplate 30s/60s; SAML 10s/10s; SMTP 5s/3s/5s; Redis 2s; PG statement_timeout 120s; ES defaults bounded. DocuSign requests unbounded (INT-2). |
