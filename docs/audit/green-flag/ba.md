## 3. P0 Acceptance Criteria (WHEN / SHALL)

### AC-LEAVE
1. WHEN an employee submits a half-day leave with startDate != endDate, the system SHALL reject the request with HTTP 400 ("half-day must be single day"). [BA-3]
2. WHEN a leave request is rejected via the approvals inbox (workflow path), the system SHALL release exactly the reserved pending days so that available balance equals its pre-request value. [BA-2]
3. WHEN an employee already has a PENDING or APPROVED leave overlapping [start,end], the system SHALL reject any new or edited request overlapping that range, including under concurrent submission (DB constraint). [BA-6]
4. WHEN a leave range spans tenant public holidays or weekends, the system SHALL deduct only working days from the balance. [BA-7]
5. WHEN a leave request is edited while PENDING, the system SHALL recompute totalDays server-side and re-reserve the new amount, releasing the old reservation. [BA-4]
6. WHEN a request violates LeaveType.maxDaysPerRequest, maxConsecutiveDays, or genderSpecific, the system SHALL reject it with the violated rule named. [BA-9]
7. WHEN an employee whose status is not ACTIVE (or NOTICE_PERIOD where policy allows) submits a leave, the system SHALL reject it. [BA-13]

### AC-PAYROLL
8. WHEN a payroll run is processed for period P, each payslip SHALL reflect presentDays/leaveDays derived from attendance and approved leave in P (not constants), and SHALL include all unapplied PayrollAdjustments (LOP deductions, overtime, expense reimbursements) effective in or before P, marking them consumed. [BA-1]
9. WHEN an unpaid (LOP) leave is approved before the period is LOCKED, the corresponding payslip SHALL show the LOP deduction; WHEN that leave is cancelled before LOCK, the deduction SHALL be voided; WHEN cancelled after LOCK, a reversing earning SHALL appear in the next run (arrears). [BA-11]
10. WHEN an approved encashment exists, the next payroll run SHALL include an encashment earning of (basic/30 × days) on the payslip. [BA-12]
11. WHEN a payroll run is LOCKED, the system SHALL reject any update/delete/reprocess of that run and its payslips (verified implemented — keep regression test).

### AC-APPROVALS
12. WHEN a leave request is created, exactly ONE approval mechanism SHALL govern it; acting through any UI surface SHALL update the same workflow execution, and no approval task SHALL remain pending after the entity reaches a terminal status. [BA-5]
13. WHEN a new tenant is provisioned, default workflow definitions for LEAVE_REQUEST, EXPENSE_CLAIM, ONBOARDING (min.) SHALL exist such that the first leave/expense submission succeeds without admin setup. [BA-8]
14. WHEN any step rejects, the whole instance SHALL be REJECTED, requester notified, and downstream steps aborted (verified implemented).
15. WHEN an approver has an active delegation or is on approved leave, new tasks SHALL be assigned to the delegate / next available manager (verified implemented).

### AC-ATTENDANCE / ONBOARDING / EMPLOYEE
16. WHEN an employee misses a punch, they SHALL be able to request regularization and the manager SHALL be able to approve/reject it, with the attendance record updated accordingly (verified implemented).
17. WHEN a new hire is assigned an onboarding template, all template tasks SHALL be instantiated on their journey and individually trackable to completion (verified implemented).
18. WHEN an employee submits a profile change to HR-approval-gated fields (bank, address), the change SHALL NOT be visible on the record until HR approves (verified implemented — `SelfServiceService`).
