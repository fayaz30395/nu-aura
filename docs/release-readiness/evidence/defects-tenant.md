# Tenant isolation + RBAC defects (agent: tenant, 2026-11-15). All reproduced at least twice.

| ID | Sev | Summary |
|---|---|---|
| DEF-TENANT-01 | High | Global `permissions` catalog table is hard-stamped `tenant_id NOT NULL = NuLogic` (660e8400-...-0001) for all 405 rows, and the `Permission` JPA entity has no `tenant_id` field at all (relies entirely on RLS to scope reads, which it cannot do here since the column is never null for any row). RLS policy admits `tenant_id IS NULL` as the "global catalog" escape hatch (same pattern used for `app_permissions`/`nu_applications`, both correctly NULL), but `permissions` was never migrated to that pattern. Effect: `role_permissions` rows in any non-NuLogic tenant point at a `permission_id` FK the app role can never SELECT under that tenant's GUC, so (a) `RoleManagementService.createRole`/`assignPermissions` (`PermissionRepository.findByCodeIn`) silently returns 0 matches for a brand-new tenant and (b) any user whose role carries a permission ends up with `AuthenticationException: Unable to find com.nulogic.domain.user.Permission with id ...` on login — reproduced live (`evidence/logs/NU-SEC-TENANT-001-login-permission-catalog.txt`). Confirmed by attempting `UPDATE permissions SET tenant_id=NULL` (aborted — NOT NULL constraint, see `evidence/logs/config-changes.md` T3) and by seeding a real tenant the way `TenantProvisioningService` does it (role_permissions copied with valid FKs) — login then fails for every role except SUPER_ADMIN (permission-check bypass by role, not by permission lookup). Files: `backend/src/main/java/com/nulogic/domain/user/Permission.java` (no tenant_id field), `infrastructure/user/repository/PermissionRepository.java`, migration history (`permissions` table DDL has `tenant_id uuid NOT NULL`). Fix: make `permissions.tenant_id` nullable and backfill existing 405 rows to NULL (matching `app_permissions`/`nu_applications`), since the permission catalog is logically a platform-wide constant, not per-tenant data; add a regression test that provisions a second tenant and asserts its default role actually carries permissions. Effort M (one forward-only migration + verifying no code path assumes non-null tenant_id on this table). |
| DEF-TENANT-02 | Medium | `GET /api/v1/knowledge/wiki/pages/{id}` (and `.../export`) throws HTTP 500 for every caller, including the page's own tenant/owner — Hibernate batch UPDATE on page-view tracking binds the `content` column (type `jsonb`) as `character varying`, and Postgres rejects the implicit cast (`column "content" is of type jsonb but expression is of type character varying`). Pre-existing bug, not introduced by or specific to this audit, but it blocked 5 of the planned wiki cross-tenant isolation checks (status NOT TESTED, not PASS). Files: wiki page read-path (`last_viewed_at`/view-count update), entity mapping for `wiki_pages.content`. Evidence: `backend-session.log` lines ~182153-182411 (`16:32:10.409`), `evidence/logs/NU-SEC-TENANT-100-idor-get-by-id.txt`. Fix: map `content` with `@JdbcTypeCode(SqlTypes.JSON)` (or equivalent) so Hibernate binds it as jsonb on every write path, not just insert. Effort S. |
| DEF-TENANT-03 | Medium | File-download tenant guard (`FileUploadController.assertTenantOwns`, `api/document/controller/FileUploadController.java:234-243`) is a bare `objectName.startsWith(tenantId + "/")` string check with no path normalization, so `../`, `%2e%2e/`, URL-encoded (`%2F`) and doubled `../../` traversal segments inside `objectName` all pass the guard (HTTP 200 on `/files/download`, `/download/direct`, `/exists` for 12/12 traversal variants tried as the wrong tenant). No file content or existence actually crossed tenants in this run only because the independent second check — `GoogleDriveStorageProvider.resolveDriveFileId` querying `drive_file_mapping WHERE object_name = ? AND tenant_id = ?` — still failed to find a row for the crafted path (the traversal string as a whole doesn't match the stored canonical path), so the real protection is defense-in-depth #2, not #1. If a future code path trusts `assertTenantOwns` alone (e.g. a new endpoint that reads `file_metadata` by `storage_path` directly, as `/exists` partially does), traversal would be exploitable. Files: `api/document/controller/FileUploadController.java:234-243`. Evidence: `evidence/logs/NU-SEC-TENANT-105-file-guard-variants.txt`. Fix: reject any `objectName` containing `..`, `%2e`, or that doesn't resolve via `Path.normalize()` to a path still prefixed by `tenantId + "/"`, before the `startsWith` check. Effort S. |
| DEF-TENANT-04 | Medium (informational, not a leak) | SUPER_ADMIN's `/api/v1/admin/system/tenants`, `.../tenants/{id}/metrics`, `/admin/system/overview` endpoints are intentionally cross-tenant (code comment: "SuperAdmin system-wide mission control... Provides cross-tenant visibility and control") and correctly return 403 for every other role tested (`tenant_admin`, `hr_admin`, `employee`). Flagging only so release sign-off explicitly acknowledges this is the one surface where a single compromised SUPER_ADMIN credential sees every tenant's name, employee/user counts, and storage usage — worth a prod-only audit-log alert on access, not a code fix. Evidence: `evidence/logs/NU-SEC-TENANT-106-public-and-platform-surface.txt`. |
| DEF-TENANT-05 | Medium | `tenants` table has `relrowsecurity = false` (no RLS at all) — confirmed live: as the app role `hrms_user` with **no** `app.current_tenant_id` GUC set, `SELECT * FROM tenants` returns all 4 rows (name, code, status, contact_email, contact_phone, country, timezone) with zero tenant context. Every other business table in the schema (325/337) fails closed without the GUC; this one does not, which is inconsistent with the documented "fail-closed" posture (`RlsStartupProbe` javadoc) and is a soft spot if the app role's credential or a future low-trust service ever gets a raw-SQL path. Low practical severity today (app code never executes caller-controlled SQL against this table). Evidence: `evidence/logs/NU-SEC-TENANT-020-rls-sweep.txt` (`tenants` listed under "NO GUC returns rows", 4). Fix: enable + force RLS on `tenants` with a policy allowing `id = current_setting('app.current_tenant_id')::uuid` for normal reads, while keeping a separate, explicitly-audited path for SUPER_ADMIN's cross-tenant list. Effort S. |
| DEF-TENANT-06 | Medium (defense-in-depth) | The application's own Postgres role `hrms_user` **owns** all 337 public tables (migrations run as this role), so it can run `ALTER TABLE ... NO FORCE ROW LEVEL SECURITY` or `TRUNCATE` on any tenant table — confirmed live on a throwaway table with the identical RLS pattern as production (owner-with-FORCE sees 0 rows under a foreign GUC; the same owner's `ALTER ... NO FORCE` immediately restores full visibility, with no RLS violation and no special privilege beyond ownership). RLS's "fail-closed" guarantee therefore depends entirely on no code path ever executing attacker-influenced raw SQL/DDL with this credential — true today (`JOOQ`/Hibernate parameterized queries only; `nu_app_rls` low-privilege role exists per migration V179 but was not the role actually used by the running app or available in this session to confirm it's wired for prod). Evidence: `evidence/logs/NU-SEC-TENANT-021-rls-writes.txt` (W8). Fix: confirm (ideally in CI) that the prod `SPRING_DATASOURCE_USERNAME` is `nu_app_rls` (a non-owning role with only DML grants), not the migration-owning role; if it's currently the owning role, switch it. Effort M (infra config, not code). |

## Not a defect — confirmed working as designed (listed for completeness, per audit-method rule "reproduce before logging")

- Tenant-id tampering via header/query/body is ignored for authenticated requests (JWT tenant claim is authoritative) — `TenantFilter.java:106-144`; live-reverified, not re-logged as a defect.
- JWT claim tampering (6 forgery variants x 3 transports = 18 probes) uniformly rejected — signature validation holds.
- Cross-tenant reference creation (pointing a new row's FK at a victim tenant's entity id) is rejected by tenant-scoped FK lookups in the service layer (`"Job opening not found"`, `"Review cycle not found"`), not by a generic 403 — i.e. the isolation is enforced at the data-access layer, not just the controller.
