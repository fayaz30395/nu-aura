# ADR-005 — Auth model: JWT in httpOnly cookie carrying roles only; permissions from DB+Redis; Google OAuth

> Reverse-engineered ADR documenting a decision already realized in the codebase.
> See [[Architecture-Decisions]] · [[Roles]] · [[Permissions]] · [[RBAC-Matrix]] · [[Middleware]].

## Status

**Accepted** — implemented and hardened across the request lifecycle. Verified against
`backend/.../api/auth/controller/AuthController.java`,
`common/security/JwtAuthenticationFilter.java`, `common/security/JwtTokenProvider.java`,
`common/config/CookieConfig.java`, `common/security/TokenBlacklistService.java`,
`application/auth/service/AuthService.java` (`googleLogin`),
`api/auth/dto/GoogleLoginRequest.java`, and `frontend/lib/api/client.ts`.

## Context

NU-AURA serves a distributed workforce across a SPA frontend and a stateless Spring
Boot backend that scales horizontally on K8s. Auth had to be **stateless** (no server
session affinity) yet **safe against XSS token theft and tenant spoofing**, support
**Google OAuth** sign-in, and drive a fine-grained **9-role RBAC** model with
per-permission authorization — without bloating the token.

Storing tokens in `localStorage` exposes them to XSS. Embedding full permission sets in
the JWT inflates the cookie past the 4096-byte limit (BUG-012). The frontend talks to a
single origin via the Next.js proxy ([[ADR-004]]), so cookies must be hardened against
sibling-subdomain planting and CSRF.

## Decision

**JWT stored only in an httpOnly cookie; the token carries roles (and tenant), not
permissions; permissions are resolved from DB and cached in Redis.**

- **Login & cookie issuance** — `AuthController` exposes `POST /login`, `POST /google`
  (Google OAuth, `AuthService.googleLogin`), `POST /mfa-login`, `POST /refresh`. On
  success it **sets secure httpOnly cookies and strips the tokens from the response
  body** so they live only in the cookie jar.
- **Cookie hardening** (`CookieConfig`) — `HttpOnly` (blocks JS access, XSS defense),
  `Secure`, `SameSite=Lax`, and the `__Host-hrms-access` / `__Host-hrms-refresh`
  prefix (browser only accepts with `Secure`, `Path=/`, no `Domain` — blocks
  sibling-subdomain planting). Legacy `access_token`/`refresh_token` names accepted
  during rollover.
- **Token content** — JWT carries `username`, `tenantId`, and **roles only**.
  Permissions were deliberately moved out of the JWT (BUG-012) to keep the cookie under
  4096 bytes.
- **Authorization** — `JwtAuthenticationFilter` validates the cookie, rejects suspended
  tenants (`TenantStatusCache`, 30s), and hydrates authorities; permissions are loaded
  by role from DB and cached in Redis (`PERMISSIONS`, `ROLE_PERMISSIONS` caches,
  [[ADR-003]]). Enforcement via `@RequiresPermission` / `PermissionAspect` /
  `CustomPermissionEvaluator` / `RoleHierarchy`, plus field-level `FieldPermission`.
- **Tenant authority** — the JWT `tenantId` claim is authoritative; the `X-Tenant-ID`
  header is ignored once a cookie is present (anti-spoof, [[ADR-002]]).
- **Revocation** — stateless tokens are revoked via `TokenBlacklistService`
  (logout, password change, "logout everywhere", impersonation) ([[ADR-003]]).
- **Silent refresh** — the Axios interceptor catches `401` and serializes refresh
  through a shared mutex hitting `POST /auth/refresh`; the backend rotates tokens
  (mint new before revoking old). CSRF uses a double-submit cookie
  (`CsrfDoubleSubmitFilter`).
- **Alternative auth** — API keys (`ApiKeyAuthenticationFilter`) and SAML 2.0 SSO
  (`SamlSecurityConfig`) coexist for integrations and enterprise sign-in.

## Consequences

### Positive

- **Stateless + scalable** — no server-side session store; any pod can serve any
  request.
- **XSS-resistant** — tokens are never readable by JavaScript and never leave the
  cookie jar (body stripped after auth).
- **Spoof-resistant tenancy** — JWT claim wins over header; suspended tenants blocked
  before context is set.
- **Small, fresh permissions** — roles in the token keep it small; permissions resolve
  from DB+Redis, so a permission change takes effect on cache expiry without re-issuing
  tokens.
- **Revocable despite statelessness** — blacklist + "revoked-before" markers close the
  logout / compromise gap.

### Negative

- **Revocation depends on the blacklist** — a stateless JWT is otherwise valid until
  expiry; Redis-backed revocation (with per-pod fallback) is the mitigation.
- **Permission-cache staleness window** — a just-changed permission can lag by the
  cache TTL; acceptable for this RBAC model but must be understood.
- **Cookie-size discipline required** — the BUG-012 lesson (permissions out of the
  token) must be respected; adding claims risks the 4096-byte ceiling.
- **CSRF complexity** — cookie auth mandates the double-submit CSRF mechanism for
  state-changing requests.

## Alternatives Considered

- **JWT in `localStorage` / Authorization header** — rejected: XSS-exfiltratable; the
  bearer-header path exists but is **off by default in prod**
  (`app.security.allow-bearer-header`).
- **Full permissions embedded in the JWT** — rejected (BUG-012): blows the 4096-byte
  cookie limit and makes permission changes require re-login.
- **Server-side stateful sessions** — rejected: needs sticky sessions or a shared
  session store, undercutting stateless horizontal scale.
- **OAuth-only / SSO-only** — rejected as the sole path: password login, MFA, API keys,
  and SAML must coexist for different user and integration classes.
