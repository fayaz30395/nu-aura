# ADR-001 — DDD-layered Spring Boot backend (api → application → domain → infrastructure + common)

> Reverse-engineered ADR documenting a decision already realized in the codebase.
> See [[Architecture-Decisions]] · [[System-Overview]] · [[C4-Container]] · [[C4-Component]].

## Status

**Accepted** — implemented and load-bearing. Verified against
`backend/src/main/java/com/nulogic/` (top-level packages: `api`, `application`,
`domain`, `infrastructure`, `common`, plus `HrmsApplication.java`).

## Context

NU-AURA is a **multi-tenant HR platform delivered as four sub-apps** ([[Nu-HRMS]],
[[Nu-Hire]], [[Nu-Grow]], [[Nu-Fluence]]) behind one login. It needed a single
deployable that could host ~67 bounded contexts per layer without collapsing into a
big-ball-of-mud, while keeping each domain's slice cohesive and independently
evolvable.

A microservices-per-domain split was rejected for an internal platform of this
team size: it would multiply operational surface (deploys, network hops, distributed
transactions) for a workload that fits comfortably in one process. The requirement
was therefore a **modular monolith** with strict internal boundaries rather than
physical service boundaries.

Evidence the platform is a single Spring Boot deployable on Java 21:
`backend/src/main/java/com/nulogic/HrmsApplication.java` (entry point);
`docs/architecture/backend.md` (Spring Boot BOM 3.5.14, Java 21).

## Decision

Adopt **Domain-Driven Design layering** with five top-level packages under
`com.nulogic`, each bounded context appearing as a vertical slice across the first
four:

| Layer | Package | Responsibility | Depends on |
|-------|---------|----------------|------------|
| API (inbound adapter) | `com.nulogic.api.<ctx>` | `@RestController`, request/response DTOs, MapStruct mappers, OpenAPI annotations | application |
| Application (use cases) | `com.nulogic.application.<ctx>` | `@Service` orchestration, `@Transactional` boundaries, cache put/evict, event publishing, schedulers | domain, infrastructure |
| Domain (model) | `com.nulogic.domain.<ctx>` | JPA `@Entity` extending `TenantAware`/`BaseEntity` | common/entity |
| Infrastructure (outbound adapter) | `com.nulogic.infrastructure.<ctx>` | Spring Data repositories, Kafka, Elasticsearch, WebSocket, Google Drive, SAML/API-key adapters | domain |
| Common (cross-cutting) | `com.nulogic.common.*` | Config, security filters, base entities, exceptions, metrics, health | — |

Dependency direction flows inward (api → application → domain) with infrastructure
as outbound adapters, the classic ports-and-adapters / hexagonal shape. Cross-cutting
concerns are isolated in `common` (`SecurityConfig`, `CacheConfig`,
`TenantRlsTransactionManager`, `GlobalExceptionHandler`).

**Base-entity convention** (`com.nulogic.common.entity/`): `BaseEntity` (UUID id +
audit columns + optimistic `version`), `TenantAware` (immutable `tenantId`), and
`TenantEntityListener`. Repositories extend `SoftDeleteJpaRepository`. Errors flow
through `GlobalExceptionHandler` (`@RestControllerAdvice`) returning a typed
`ErrorResponse`.

## Consequences

### Positive

- **Cohesive vertical slices** — each context (`employee`, `payroll`,
  `recruitment`, `knowledge`, …) is editable end-to-end without cross-cutting
  ripple; new contexts add a slice in four packages.
- **Single deployable, simple ops** — one JVM, one Flyway chain, no inter-service
  network calls for the common path; supports K8s scale-out of identical pods.
- **Enforced inward dependency** — controllers cannot reach repositories directly;
  business rules live in the application/domain layers, keeping adapters thin.
- **Shared cross-cutting baseline** — tenancy, caching, security, and error
  handling are implemented once in `common` and inherited everywhere
  (see [[ADR-002]], [[ADR-003]]).

### Negative

- **Boundaries are convention, not compilation-enforced** — nothing physically
  stops an `api` class importing a repository; discipline (and review) is required.
- **Layer ceremony** — a trivial endpoint still touches controller → service →
  repository → mapper, more files than a flat design.
- **Shared database couples contexts** — all slices share one schema and connection
  pool, so a hot context can affect neighbours (mitigated by caching, [[ADR-003]]).

## Alternatives Considered

- **Microservices per bounded context** — rejected: operational and distributed-
  transaction cost is unjustified for an internal single-team platform.
- **Flat package-by-technical-type** (`controllers/`, `services/`, `entities/`) —
  rejected: scatters each domain across the tree, defeating cohesion at ~67 contexts.
- **Spring Modulith with verified module boundaries** — a viable future hardening
  step (would make the inward dependency rule compile-checked), but not adopted at
  decision time.
