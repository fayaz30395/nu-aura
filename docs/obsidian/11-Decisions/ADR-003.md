# ADR-003 — Redis as the platform coordination substrate (cache tiers, rate limiting, token blacklist, idempotency, edit locks, WebSocket relay)

> Reverse-engineered ADR documenting a decision already realized in the codebase.
> See [[Architecture-Decisions]] · [[Services]] · [[Data-Flows]] · [[Deployment]].

## Status

**Accepted** — Redis 7 is the distributed coordination layer across the platform.
Verified against `backend/.../common/config/CacheConfig.java`,
`common/config/DistributedRateLimiter.java`, `common/security/TokenBlacklistService.java`,
`infrastructure/kafka/IdempotencyService.java`,
`application/knowledge/service/FluenceEditLockService.java`,
`infrastructure/websocket/` (`RedisWebSocketRelay`), and [[Code-Patterns]].

## Context

NU-AURA runs as **multiple identical pods on Kubernetes** (GCP GKE). Several
cross-cutting concerns must be **consistent across all pods**, not per-instance:
reference-data caching, rate limiting, JWT revocation, Kafka deduplication,
collaborative edit locks, and WebSocket fan-out. A per-instance counter or in-memory
map breaks each of these as soon as there is more than one pod.

At the same time, none of these concerns may take the whole API down if the coordination
store is briefly unavailable — a Redis outage must degrade, not fail hard.

## Decision

Use **Redis 7 as the single distributed coordination substrate**, with each consumer
degrading gracefully on Redis failure:

| Concern | Component | Mechanism | Failure mode |
|---------|-----------|-----------|--------------|
| Caching | `CacheConfig` (25 named caches) | `@Cacheable` on Redis; tenant-scoped keys `tenant:{id}:{Class}:{method}:{params}`; tiered TTLs 30s–24h | `CacheErrorHandler` bypasses to DB |
| Rate limiting | `DistributedRateLimiter` + `RateLimitingFilter` | Redis Lua `INCR`+`EXPIRE` (sliding window); per-tenant multi-token buckets | Bucket4j in-memory fallback; AUTH fails closed, rest fail open |
| Token revocation | `TokenBlacklistService` | `token:blacklist:{jti}` + user/tenant "revoked-before" markers, TTL = token lifetime | per-pod in-memory fallback; 30s health probe re-arms Redis |
| Kafka dedup | `IdempotencyService` | atomic `SETNX` `kafka:idempotent:{eventId}`, 24h TTL, plus `release()` on failure | fail-open (DB constraints are net) |
| Edit locks | `FluenceEditLockService` | `fluence:edit-lock:{tenant}:{type}:{id}`, 5min TTL, owner-aware | lock simply not held |
| WebSocket relay | `RedisWebSocketRelay` / `RedisWebSocketSubscriber` | Pub/Sub multi-pod fan-out for STOMP | local-only delivery |

> **Railway / no-Kafka environments:** a **transactional-outbox** pattern
> (`OutboxEventProcessor`, enabled by `app.outbox.enabled=true` default) supplements
> Kafka. Events are written atomically to `outbox_events` (PG table, V300 + V303 RLS)
> and polled every 5 s by a scheduler; this makes event delivery durable even when
> Kafka is unavailable. See `infrastructure/kafka/outbox/OutboxEventProcessor.java`.

The cache manager is `@ConditionalOnBean(RedisConnectionFactory.class)` so Redis
absence disables caching rather than failing startup. Cache keys are **tenant-scoped**
via `keyGenerator()` to prevent cross-tenant cache collisions (ties into [[ADR-002]]).
Note: scheduled-job locks deliberately use **ShedLock on PostgreSQL**, not Redis,
because they gate data-mutating cron work and must be correct even if Redis is down.

## Consequences

### Positive

- **Cross-pod consistency** — one rate-limit budget, one revocation list, one
  idempotency claim, one cache, regardless of pod count.
- **Latency and DB-load relief** — hot reference data (roles, permissions,
  departments, leave types) served from Redis with TTLs tuned 30s–24h.
- **Uniform graceful degradation** — every Redis path has an explicit fallback or
  fail policy, so a Redis blip never returns 500s for the whole API.
- **Reused primitive** — one operational dependency backs six concerns instead of six
  bespoke mechanisms.

### Negative

- **Redis is a shared hot dependency** — degraded mode is correct but lossy (per-pod
  rate limits, best-effort revocation, possible duplicate Kafka processing).
- **TTL/eviction tuning is ongoing** — wrong TTLs cause stale reads or thundering
  herds; mitigated by `CacheWarmUpService` and per-cache tiers.
- **Two lock mechanisms to reason about** — Redis edit locks vs ShedLock DB locks;
  the split is intentional but adds conceptual surface.

## Alternatives Considered

- **In-memory caches/counters per pod** — rejected: inconsistent across pods,
  bypassable rate limits, no shared revocation.
- **Database-backed cache and counters** — rejected for hot paths: defeats the goal of
  taking read load off PostgreSQL.
- **Hazelcast / other distributed cache** — rejected: Redis already required for
  Pub/Sub and locks; adding a second clustering layer is unjustified.
- **Redis for scheduled-job locks too** — explicitly rejected; cron correctness must
  survive a Redis outage, hence ShedLock-on-Postgres.
